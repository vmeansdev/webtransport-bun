# Home-rig 3k: close the ack-tail gap

Status: DRAFT for Architect → Critic review. Execution starts only on two
unconditional APPROVEs.

## 1. Problem, measured

Rig: gravvene-dev-home (Ryzen 5 3550H, 4c/8t, 12 GB, eno1 1 GbE, r8169
single queue) ↔ Mac generator over 10.99.0.0/24. Candidate `2eeeaa91`,
profile 4 shards × 2 workers, native ack reflector, GRO off, paced connect
250/s, 128 endpoints. Grader: `tools/load/g6-sharded-grade.ts` clauses
S1 ingest ≥ 0.995, S2 delivery ≥ 0.995, S3 duty ≥ 0.99, S4 ack p99 ≤ 25 ms,
S5 lost ≤ 0.1 %.

| sessions | S1 | S2 | S4 p99 | cores/8 | verdict |
|---|---|---|---|---|---|
| 2750 | 1.000 | 1.000 | 7.2 ms | 5.3 | CLEAN |

Only S4 fails at 3000. Ingest is perfect to 7500 and there are zero kernel
UDP drops at every rung, so the tail is queueing inside the process.

## 2. Where the 20 ms is (code-bound)

The ack path for one action datagram (`crates/native/src/lib.rs:1660-1730`):

1. The endpoint driver (a task on the shared `wt-server` tokio pool in
   `shared` mode, `quic_runtime.rs:141-147`; a dedicated thread in
   `dedicated` mode) receives the UDP packet and hands it to the
   connection.
2. The connection driver task (always on the shared pool) decrypts and
   delivers the DATAGRAM frame to the session's forward task.
3. The forward task matches the reflector rule, builds the reply, measures
   `hold` (receive → build, `lib.rs:1690-1727`) and hands the send to the
   `wt-reflect-sender` thread (`datagram_reflector.rs:312-333`).
4. That thread calls `send_datagram`, which enqueues on the connection and
   wakes the connection driver.
5. The connection driver, when a worker next polls it, packetises, encrypts
   and writes the UDP packet.

Steps 2 and 5 wait in the shared pool's run queues. Egress is generated by
the JS emitter at 50 Hz slices (`g6_protocol.rs:17`, a registered
constant) through `send_datagram_mirror_for_owner` (`session.rs:230-254`),
which performs ~675 `send_datagram` calls per shard per 20 ms slice at
3000 sessions; each wakes a connection driver. A worker therefore serves a
burst of ~675 driver polls, and the action's two driver polls queue
behind it. The reflect `hold` histogram cannot see this (it spans only
step 3), which is why the server looked idle while the client tail grew.

Evidence gap: the reflect hold histogram and `datagram_reflect_queue_full`
exist in `ServerMetrics` but are not written into the shard boundary
snapshot, so no scan so far can locate the queue from the server side.

## 3. Levers, cheapest first

**L0a — dedicated receive runtime (existing knob, zero code).**
`SCAN_SERVER_RECV_RUNTIME=dedicated` moves step 1 off the shared pool
(`quic_runtime.rs:74-147`). Regressed on c-48 at 30k (r99) but has never
been measured on a 4-core box where the pool is the contended resource.

**L0b — paced emitter (existing knob, zero code).** `G6_PACED_EMITTER=1`
plus `WEBTRANSPORT_PACER_PPS` spreads the slice's sends across the slice
(`egress_pacer.rs`, `send_datagram_mirror_paced_for_owner`), shrinking the
burst the action's driver polls wait behind. At 3000 sessions the box
emits 45,000 snapshot datagrams/s; per shard 11,250 pps. The pacer thread
already honours `WEBTRANSPORT_PACER_NICE`/`_SCHED`. Note the scan warning
at `g6-sharded-scan.ts:814-818`: run as root so `WEBTRANSPORT_PACER_PPS`
reaches the shards (the home recipe already uses `sudo env … PATH`, which
passes only the named variables, so the pacer variables must be named on
the sudo line explicitly).

**L1 — thread priority for the two ack-path threads (small code change).**
Give the `wt-reflect-sender` thread and the dedicated reader thread the
same nice/SCHED_RR treatment the pacer thread has, so that when the pool is
saturated the kernel still schedules them promptly. This does not fix
steps 2 and 5 (they are pool tasks), so on its own it is expected to be a
partial lever; it is cheap and reuses proven code.

**L2 — scheduler fairness knobs on the shared pool (small code change).**
Expose tokio's `event_interval` and `global_queue_interval` on the
`RUNTIME` builder (`lib.rs:185-197`) through env, so a worker checks the
I/O driver and the global queue more often inside an egress burst. This
is the only lever that shortens steps 2 and 5 without restructuring.

**L3 — surface the evidence (small code change, needed for any verdict).**
Write `datagramReflectHold` (p50/p99/max) and `datagramReflectQueueFull`
from `metricsSnapshot()` into the shard boundary record and the scan's
per-shard window, so the A/B can prove whether the residual tail is in
steps 3-4 (reflect path) or steps 2/5 (pool).

Rejected: fewer workers (doubled the tail), GRO on (wrong-shard drops,
r95 root cause), relaxed ACK cadence (+max RTT, 20k connect failures),
changing `EMITTER_SLICE_HZ` (registered protocol constant), a second
reflector runtime (quinn requires the connection driver for every send, so
a separate runtime cannot bypass steps 2/5).

## 4. Plan

Pass criterion for every arm: at 3000 sessions, S1-S3 and S5 pass and S4
≤ 25 ms, replicated in two consecutive cells. Box quiet (QEMU VM
SIGSTOPped) for every cell so arms are comparable to the 44 ms baseline.

### Phase 0 — knob A/Bs, no code (≈ 15 min)
- P0.1 `dedicated` recv runtime at 3000.
- P0.2 paced emitter at 3000, `WEBTRANSPORT_PACER_PPS=12000` per shard
  (11,250 demand + 6 % headroom), `WEBTRANSPORT_PACER_NICE=-10`.
- P0.3 both together if either moves S4 by ≥ 10 ms.
Deliverable: table of S1-S5 + cores per arm. If any arm passes twice, stop
here and record the home max at 3000 with that profile.

### Phase 1 — code (only if Phase 0 fails), ≤ 5 files
- T1 `crates/native/src/thread_priority.rs`: move `PriorityRequest`,
  `parse_priority`, `apply_priority`, `PriorityAchieved` out of
  `egress_pacer.rs` into a shared module parameterised by env prefix;
  `egress_pacer.rs` keeps its behaviour byte-for-byte (existing tests
  stay green). Unit tests: parsing, clamping, malformed.
- T2 apply it to `wt-reflect-sender` (`datagram_reflector.rs:312`) under
  `WEBTRANSPORT_NATIVE_REFLECT_NICE` / `_SCHED`, and to the split
  runtime's reader thread (`quic_runtime.rs:97-116`) under
  `WEBTRANSPORT_NATIVE_READER_NICE` / `_SCHED`; achieved priority
  exported in `metricsSnapshot()` next to the pacer's.
- T3 tokio knobs: `WEBTRANSPORT_NATIVE_SERVER_EVENT_INTERVAL` and
  `WEBTRANSPORT_NATIVE_SERVER_GLOBAL_QUEUE_INTERVAL` on `RUNTIME`
  (`lib.rs:185-197`), fail-closed parsing like `server_worker_threads`,
  values echoed by a getter so the scan can pin them.
- T4 (L3) boundary evidence: `g6-shard-server.ts` boundary includes
  `datagramReflectHold` and `datagramReflectQueueFull` from
  `metricsSnapshot()`; the scan carries them per shard per window; a
  source test asserts the keys on both sides (producer/consumer key test,
  the r100 lesson).
- T5 scan passthrough: the new env names travel to shard children on both
  spawn branches; `SCAN_*` mirrors with fail-closed validation; the
  ready-message echo check for each, as done for `serverAckCadence`.
Gates: `cargo test -p native`, `bun test packages/webtransport/test`,
campaign gate suite, `bun run typecheck`, biome. Push to the probe branch.

### Phase 2 — A/B at 3000 with Phase 1 knobs (≈ 15 min)
- Arms: baseline; reflect+reader nice -10; RR:50 on both; tokio
  event_interval 16 / global_queue_interval 8; best two combined; plus the
  Phase 0 winner if any. Two cells for any arm that passes.
- Verdict recorded in memory and `.omx/ultragoal/ledger.jsonl`; the
  reflect-hold and queue-full evidence says which step the residual lives
  in.

### Phase 3 — only if Phase 2 fails
Report: the remaining tail is worker-pool queueing of the connection driver
behind egress polls and cannot be scheduled away on 4 cores; the honest
options are fewer sessions per core or a bigger box. No further code.

## 5. Risks
- SCHED_RR on a 4-core box can starve the pool if the RR thread spins; the
  reflect thread only drains a bounded channel, the reader only polls one
  socket, so both block promptly. Measure, do not assume.
- Running the rig as root with `sudo env` passes only named variables; a
  forgotten name silently disables a knob. T5's ready-message echo makes
  that fail closed.
- The Mac generator is at 3.5 cores at 5000; not a limiter at 3000.
