## Finding driving the amendment

The B5 Critic (stage `fanout-pilot-r1` at `efaed8bb`, `.release-evidence/transport-comparison/.trust-staging/efaed8bb…/fanout-pilot-r1/reviews/critic.md`) refused launch: the frozen `ticker-fanout/rate-10000` cell requires 10,000,000 deliveries in a 10 s window (1,000,000/s). One relay-to-subscriber `FanoutDataV1` frame is 654 B, so the cell declares 5.2 Gbit/s against a 1 Gbit/s cable, and the rig relay (one Bun loop) encodes ~48k such deliveries/s. The run would have sealed two PASS entries with totals two orders of magnitude below the gate, destroyed both keys, and B6's ticker rows (26–52 Gbit/s) would have followed. The base plan carries no link or CPU budget. The R1 review then showed the relay's cost is not one number: it grows with subscriber count, and a WebTransport stream write is paid on the relay's own thread.

**Row ceiling (per transport, per topology):** `ceiling(K, t) = 1 / (relay_us(K) + send_us(t))`, with `relay_us` interpolated linearly between the measured K points (never extrapolated below K=100 or above K=5,000), `send_us` = 1.0 (WS) / 12.0 (WT: 7.0 write + 5.0 completion). The combined runs confirm the model's ceilings (K=100 model 90k vs measured 90–95k; K=2,500 model 67.8k vs measured 73–75k) but show that utilisation below the ceiling is 30–50 % higher than the model because of the settler's `counters()` calls; the rule therefore binds on **measured main-thread utilisation**, not on the model.

**Binding rate of a row** = max(measured-window deliveries/s, warmup deliveries/s) = the warmup rate for every chat row (2×) and the measured rate for ticker rows.

**Budget rule (binding on every row, now and later):** at the row's binding rate the server child's main thread must measure **≤ 0.50 core** on both transports (≥2× headroom, all thread costs included), and the D4 preflight, offering 2× the binding rate for the full window, must sustain it with the main thread **≤ 0.80 core**, zero faults and exact conservation. The model ceiling must additionally be ≥ 2× the binding rate (a cheap pre-check only — the measured utilisation is the rule; rate-250 on WT pre-checks at 62,189/s = 2.49×). The settler's O(K log K) `counters()` work and the lazy WT stream open are recorded as relay inefficiencies to be removed and re-measured in a later amendment; this amendment prices them as measured. The link is no longer the constraint: at 25,000 deliveries/s the frame-plus-WS-header bit rate is 25.6 Mbit/s (ticker, 128 B units) / 31.2 Mbit/s (chat, 156 B units), payload alone 20.0 / 25.6 Mbit/s, 3 % of the cable; the WT write count on the relay thread is. The 1,000,000/s cell is impossible on this cable at any frame ≥113.6 B before margin (940.7e6/8/1e6 − 4).

## D2. Compact delivery frame `fanout-delivery/c1`

Only the relay→subscriber data path changes. Publisher→relay data frames, all control frames (register/accept/refuse/warmup/end/ack) and their stream mapping stay exactly as §4.2 defines them.

Per frame, little-endian, fixed 24-byte header followed by the payload:

| off | size | field | consumer |
|---|---|---|---|
| 0 | 1 | magic `0xC1` | routing (server.ts) and decoder version gate |
| 1 | 1 | `windowIndex` u8 (< `FANOUT_MAX_WINDOW_COUNT`) | worker `deliveredByOriginWindow[w]` |
| 2 | 2 | `publisherIndex` u16 (index into the grant's `publishers[]`) | worker duplicate/reorder key |
| 4 | 4 | `subscriberIndex` u32 (index into the grant's subscriber order) | worker cross-check against its own roleId |
| 8 | 4 | `publisherSequence` u32 | worker duplicate/reorder key |
| 12 | 4 | `linuxAcceptedOrdinal` u32 | states Linux authorship (§4.2) |
| 16 | 4 | `contextTag` u32 = first 4 LE bytes of the session's `deliveryContextSha256` | binds every frame to the grant and epoch the subscriber was admitted under; selects warmup vs measured accounting |
| 20 | 2 | `payloadBytes` u16 = cell `messageBytes` | conservation of bytes |
| 22 | 2 | reserved, must be 0 | |
| 24 | N | payload | delivered bytes |

**Delivery channel.** Every subscriber session owns a delivery channel: WS, the socket itself (one binary message per unit); WT, the server-opened uni stream. At HEAD the WT server requests that stream at accepted subscriber registration (`server.ts:1173-1175`, since b7a93bbe) and keeps a lazy open on the first delivery-routed `trySend` as a fallback (`:1038-1069`); the role is unknown at `handle.onSession` (`:1030`) and the accept is written inside `handleRegister` (`fanout-relay.ts:676`) before the server learns the role, so no earlier point exists and no consumer depends on the accept/stream order (`fanout-role.ts:2263-2282` reads uni streams in a detached loop). This amendment keeps the request at accepted subscriber registration and **removes the lazy fallback**: a delivery unit for a subscriber whose stream is not open yet is never routed through the control path. The relay addresses the channel explicitly: `RelaySessionSink` gains `trySendDelivery(bytes)` beside `trySend` (control); delivery-context and compact frames go through `trySendDelivery` only, and `relayFrameRoutingFields`' JSON parse (`server.ts:865-915`) is never on a delivery path — which is what removes the K²/2 context-parse storm (`fanout-relay.ts:1791-1838`, ≈11 s of relay thread at K=2,500, R2 Critic §D). The delivery context is the first item of the subscriber's delivery queue: `QueuedDelivery` (`fanout-relay.ts:364-370`) gains `kind: "context" | "delivery"`; a context item is enqueued at the head under the existing per-subscriber cap and 5 s write deadline, is not counted as a delivery or as relay bytes, and is retried by the same pump; a context that cannot be written before the deadline fails the session closed like any delivery would.

**Unit encoding on the WT delivery stream.** Two unit kinds share the stream and are told apart by their first byte: `0xC1` = one compact frame of exactly `24 + messageBytes` bytes (the header states the length; no prefix); `0x00` = the existing `u32be length ‖ canonical JSON` unit (every legal JSON unit is < 16 MiB, so its first byte is always `0x00`; `fanout-wire.ts:1073-1083`). The Mac worker's uni reader (`LengthPrefixedFrameReader`, `adapters/wt.ts:2194`, used at `fanout-role.ts:2247-2256`) becomes mixed-mode: on `0xC1` it frames exactly `24 + messageBytes` bytes from the cell constant and hands the unit to the compact decoder, which refuses (`onMalformed`) immediately when the header's `payloadBytes ≠ messageBytes` or any header check fails — a wrong length is a counted refusal, never a silent stall; on `0x00` it takes the prefixed JSON path, where a prefix over the cap still throws and ends the child (FAIL through the lifecycle path, not a counter). On WS the discriminator is the same first byte of the binary message.

**Per-session delivery context.** The relay sends each subscriber exactly one JSON control frame per epoch on the **delivery channel** (WS: the next binary message; WT: the first frame on the uni stream), before any compact frame of that epoch:

- measured epoch, exact keys: `{schema:"fanout-wire/v1", kind:"delivery-context", epoch:"measured", cohortGrantSha256, cohortStartBarrierSha256, subscriberId, subscriberIndex, publisherIds, windowCount, messageBytes, deliveryContextSha256}`
- warmup epoch, exact keys: `{schema:"fanout-wire/v1", kind:"delivery-context", epoch:"warmup", cohortGrantSha256, cohortWarmupEpochSha256, warmupNonce, subscriberId, subscriberIndex, publisherIds, windowCount, messageBytes, deliveryContextSha256}`
- `deliveryContextSha256 = sha256(canonical JSON of the frame with the deliveryContextSha256 key removed)`; `contextTag = first 4 LE bytes`.

The relay enqueues the warmup context for every registered subscriber when it binds the warmup epoch (registration is closed from that point, `fanout-relay.ts:689`, so no subscriber joins later) and the measured context inside `openMeasuredWindow`, ahead of the first measured delivery; both enqueue points see empty delivery queues (`bindWarmupEpoch` requires phase `registration`; `openMeasuredWindow` requires `warmup-drained`, which `drainWarmup()` refuses to reach while `queuedItems !== 0`, `:996`). The delivery-context parser keys its forbidden-key set on `epoch` (today `rejectEpochMixing` keys on `kind.startsWith("warmup-")`, `fanout-wire.ts:371-372`; the new kind carries both epochs). The worker verifies at consumption, in inbox order: it recomputes the digest from its own admission facts (grant, barrier or warmup epoch + nonce, its roleId and index, the publisher ids, window count, message bytes) and refuses on mismatch. A compact frame that arrives on a session with no context for its tag, or with a wrong `subscriberIndex`, `payloadBytes`, `windowIndex`, magic or reserved field, is refused. Warmup and measured deliveries are told apart by the tag, replacing today's `frame.kind === "warmup-data"` test (`fanout-role.ts:1365`): the warmup loop (`:1361-1370`) refuses, not ignores, any unit that is neither the epoch's delivery context nor a warmup-tagged compact frame; a warmup-tagged frame after the measured context is refused; equal warmup and measured tags refuse the session. `drainOnce` (`:1852-1858`) carries the inbox's roleId so the book is keyed by the session, not by `frame.subscriberId` (`:1451` today). `deliveryContextSha256` is over the exact key set above (not the scratch prototype's five-field preimage, `compact-codec.ts:52-57`); slice 1's vectors are derived from this text.

**Fail-closed fault path (new; today a refused frame is silently dropped at `fanout-role.ts:2196-2197, 2252-2255` and worker counters never reach the verifier).**

1. Both worker connectors hand every decode refusal to the session (`onMalformed`) — including the WT connector's `decoded.value.length !== 1` case (`fanout-role.ts:2253`, dropped silently today) — and `WorkerWindowBook.recordMalformed` counts it; the book is keyed by the session's own roleId, never by a field of the frame.

3. `verify-artifact.ts` refuses promotion when any `WorkerPartialV1` counter (`malformedCount`, `duplicateCount`, `reorderCount`) is non-zero or when `perSubscriberDelivered[i] ≠ serverAcceptedIngress` for any subscriber, completing the §4.5 predicate whose worker half is unenforced at HEAD (`verify-artifact.ts:4124-4149`); each new refusal has a mutation test.
