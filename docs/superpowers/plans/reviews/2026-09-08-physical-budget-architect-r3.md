## D. The delivery channel at admission, against `server.ts` as written

- **WS.** `onOpen` (`server.ts:693-704`) makes the socket a relay session before the role is known; the delivery channel is the socket, so it exists at admission; the context is "the next binary message" after the epoch admits the subscriber. `session.send` answers would-block only when paused. ✓.
- **WT, where the uni stream would be created.** There is no `onOpen`; the session callback is `handle.onSession` (`:1032`), and the role is unknown there (`:958-961`). The role becomes known when `relay.handleInboundBytes` runs `handleRegister` (`fanout-relay.ts:640-677`), which writes the accept synchronously (`sendFrame :676` → `sink.trySend :1804`) before returning; the server sees the role only afterwards (`server.ts:1168-1175`) and there calls `openDeliveryStream()` (`:1173-1175`), whose `createUnidirectionalStream()` is a Promise (`:1041-1043`). So "created … before the accept frame is answered" is not buildable without either (a) opening a uni stream for every session at `onSession` (publishers included, ≤10 streams; the open callback already tolerates a session closed meanwhile, `:1044`; a refused registrant costs one stream reset) or (b) deferring the accept behind the async open — a new relay/sink contract the amendment does not specify. HEAD's actual order — open at accepted subscriber register, warmup context at `bindWarmupEpoch` (`fanout-relay.ts:3036`) seconds later — already gives "the context is the first unit on the stream" for every open that completes before the bind.
- **A subscriber refused after the stream is opened.** Cannot happen under HEAD's order (open follows acceptance); under (a) the refuse + `closeSession` path runs `session.close` → both writers closed and flushed (`:1094-1118`) and the open callback returns on `closed` (`:1044`). Bounded.
- **`trySendDelivery`.** `RelaySessionSink` is `{trySend, close}` (`fanout-relay.ts:165-168`); adding `trySendDelivery` and routing `data`/`warmup-data`/`delivery-context` through it removes `relayFrameRoutingFields` (`server.ts:865-915`) from the delivery path — implementable, and the WS sink maps both to `session.send`. What the amendment leaves unsaid: a would-block on `trySendDelivery` for the **context** ("handled by the per-subscriber queue as today") — the context is not a queued item today (`QueuedDelivery` carries fanned items, `:1369`); it must be enqueued at the head of that subscriber's queue under the same 64-item cap and 5 s deadline, or the session must fail closed if the channel is absent at the bind. Say which.
- **Ordering promises.** §4.2 (base 1428-1430) promises "each subscriber receives data on one server-opened uni stream" and the prefix, nothing about accept-vs-stream order; `fanout-relay.ts:1826` ("control frames drain before any data frame on the same session") is per-sink and survives once control and delivery are separate sinks. The worker does not depend on the order either: it registers over the control bidi and reads uni streams in a detached loop (`fanout-role.ts:2264-2274`, `send` writes without awaiting `:2277-2282`). So the "before the accept" invariant has no consumer.
- **Mixed-version safety.** `nodeWritableFrameWriter` writes any bytes as-is (`adapters/wt.ts:2302-2321`) ✓; an old Mac reader receiving `0xC1…` throws `RangeError` in `push` (`:2225-2231`) → child dies → `UNEXPECTED_EOF` → FAIL ✓ (uncounted, as D2 says).
