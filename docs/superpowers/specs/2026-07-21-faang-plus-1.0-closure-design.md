# FAANG+ Native and WASM 1.0 Closure Design

**Status:** Proposed for architect and critic approval  
**Date:** 2026-07-21  
**Branch:** `feat/wasm-1.0`  
**Baseline:** `500e66a1c525a87a03c56bc5079bd3151affe113`

## Purpose

Close every valid finding from the 2026-07-21 Sol-grade production-readiness
review, remove every known P0-P4 defect from the native and WASM surfaces, and
replace aspirational 1.0 claims with reproducible release evidence. The result
is allowed to become `1.0.0` only when the implementation, package, CI,
security posture, operational evidence, and independent re-review all agree.

“FAANG+” is treated as an evidence standard, not a brand label. In this design
it means bounded resources, deterministic lifecycle behavior, abuse-resistant
defaults, stable diagnostics, portable supported-runtime behavior, repeatable
multi-platform release construction, adversarial and browser interop proof,
and retained scale/soak evidence. A green unit suite alone is insufficient.

## Approval and execution contract

The user explicitly requested the following gate sequence:

1. Create the closure plan from the audit.
2. Obtain architect approval.
3. Obtain critic approval after the architect approves.
4. Only then create a persistent end-to-end completion goal.
5. Execute, verify, auto-review, fix, and repeat until no valid P-level finding
   remains.

The current request supplies product approval for this direction. Architect and
critic approval are the designated technical approval gates. No implementation
begins and no goal is created before both gates pass.

## Approaches considered

### A. Freeze native at 1.0 and keep `/wasm` experimental

This minimizes work and follows the older native-only hardening plan. It is
rejected because the requested release explicitly includes the WASM part and
because the package already exports `/wasm` from the same release artifact.

### B. Patch only the findings named in the audit

This is faster but leaves the historical failure mode intact: prior status
documents claimed zero known findings, then fresh review found release-blocking
security, lifecycle, portability, and packaging defects. It is rejected because
known-finding closure without proof-system closure is not a trustworthy 1.0
process.

### C. Unified native+WASM release train with convergent evidence

This is the selected approach. Known findings are fixed test-first in bounded
lanes, then the release pipeline builds and tests the exact consumer artifact,
then independent reviewers attack the resulting tree. Any valid P0-P4 finding
reopens the relevant lane and the entire affected gate is rerun.

## Non-negotiable invariants

1. **No silent loss:** a successful Promise or stream operation means the data
   was accepted under a documented bounded policy. Queue pressure waits, times
   out with `E_BACKPRESSURE_TIMEOUT`, or rejects with another stable `E_*`
   diagnostic. Silent drops and ignored boolean failures are forbidden.
2. **No unbounded wait:** every network, queue, stream, close, callback-delivery,
   and test wait has an explicit deadline or a lifecycle-driven cancellation
   path.
3. **No unbounded memory:** every JS-Rust, Rust-QUIC, WASM-host, session, stream,
   datagram, and event queue is budgeted. Reservations are released exactly
   once on dequeue, error, cancellation, and teardown.
4. **Close means closed:** a successful close proves tasks, registries, queues,
   callbacks, sessions, and sockets are drained or cancelled. A deadline breach
   is an error, never a false success.
5. **Abuse resistance is default-on:** both native and WASM server paths enforce
   session, handshake, stream, datagram, and byte limits before resource growth.
6. **Supported means continuously tested:** Bun, Node, and Deno plus macOS,
   Linux, and Windows are release gates, not documentation-only claims.
7. **Shipped artifact equals tested artifact:** the packed tarball contains the
   native prebuilds and `wasm-dist` bits used by clean consumer smoke tests.
8. **No known vulnerable shipping graph:** both Rust lockfiles and the npm graph
   pass current security audits without broad or unexplained suppressions.
9. **No stale truth documents:** `README`, parity, security, CI, operations, and
   release status must describe the exact verified commit and evidence.
10. **No accepted P-level debt:** valid P0-P4 findings are fixed. Duplicates,
    incorrect reports, and explicit non-goals may be rejected only with code or
    test evidence recorded in the review ledger.

## Component design

### 1. Shared deadline and budget semantics

Native and WASM keep separate runtime implementations, but expose the same
behavioral contract: reserve, wait for a lifecycle or capacity notification,
re-check, then either commit the operation or return a stable deadline error.
Reservations are RAII-owned in Rust and `try/finally`-owned in TypeScript.
Polling may be used only as a bounded compatibility fallback and is never tied
to `Bun` globals.

### 2. Native lifecycle hardening

The native server and client runtimes retain their dedicated ownership model.
Close becomes an explicit state machine: stop admission, signal sessions,
cancel or drain tracked work, close queues, remove registries and rate-limit
state, wait to the configured deadline, and return success only at zero owned
resources. Callback-delivery failure follows the same cleanup path as peer or
local closure.

### 3. WASM production governor

The WASM endpoint gains a focused limits/governor unit rather than adding more
unrelated responsibilities to `endpoint.rs`. It owns configuration validation,
byte reservations, stream/session counters, per-peer token buckets, monotonic
time decisions, and metrics snapshots. Endpoint transitions call the governor
before allocation and release through guards on all terminal paths.

### 4. WASM facade lifecycle

`WasmWebTransport` owns one explicit state machine aligned with the root W3C
facade. Backend callbacks settle `ready`, `draining`, and `closed` exactly once.
Writable streams map backend capacity rejection to pending Promise pressure and
deadline errors. Readable queues use byte/item strategies and stop the backend
pump when desired capacity is exhausted.

### 5. Certificate policy

The pin verifier keeps possession proof and SHA-256 matching, then applies the
browser-compatible short-lived-certificate policy using a small, bounded DER
metadata parser covered by fixtures and fuzz/property tests. This avoids adding
a dependency without approval. Any parse ambiguity rejects closed.

### 6. Artifact-first release pipeline

CI builds native prebuilds and the production WASM bundle before packing. All
consumer smoke tests install the produced `.tgz` in empty directories. Release
jobs consume the same retained artifact and verify checksums, exports, supported
runtimes, provenance configuration, and evidence JSON before a tag could be
eligible. This project will be made ready; publishing/tagging is not required
to prove readiness and remains a distinct outward release action.

### 7. Evidence ledger and review loop

A machine-readable release evidence file records commit SHA, toolchain pins,
commands, outcomes, artifact hashes, platform, and timestamps. Documentation
summarizes this file rather than independently asserting status. Final review
uses independent security, native correctness, WASM correctness, portability,
testing, release/supply-chain, performance, and operations lenses. Findings are
deduplicated into the register; any valid P0-P4 result reopens implementation.

## Testing and proof strategy

Each behavioral fix follows red-green-refactor: add the smallest regression,
observe the expected failure, implement the smallest fix, run the focused test,
then run the affected subsystem. Configuration-only changes use a failing
policy/packaging test before workflow edits.

The full exit campaign includes:

- Rust format, clippy, unit, integration, audit, and parser fuzz/property gates
  for both native and standalone WASM workspaces.
- TypeScript typecheck, lint/format, Bun suites, Node suites, Deno suites, parity,
  native/WASM interop, adversarial, abuse, lifecycle, and package-consumer gates.
- Repeated cold CI-equivalent runs to expose order, port, certificate, and
  teardown flakes.
- Benchmark regression, overload, >=10k scale, 24-hour soak, and 72-hour soak
  with retained metrics and resource-trend artifacts.
- Clean package installation on macOS arm64, macOS x64 where available, Linux
  x64, and Windows x64 through required CI jobs.

## Severity and convergence rule

- **P0:** exploitable security, unbounded resource loss, missing shipped
  artifact, data corruption, or release integrity failure.
- **P1:** production correctness/liveness failure, support-contract break, or
  missing mandatory production evidence.
- **P2:** bounded but material defect, significant test/operability gap, or
  reproducibility weakness.
- **P3:** maintainability or diagnostic weakness with a plausible future
  correctness impact.
- **P4:** minor inconsistency, stale text, or hygiene issue within release scope.

The terminal state is **zero valid open P0-P4 findings**. A reviewer report does
not automatically become truth: each item is reproduced or disproved. A
disproved item is closed with evidence; a valid item is fixed and reviewed
again. No valid item is waived merely because it is low severity.

## Definition of done

The project is ready to become `1.0.0` only when all of these are true on one
immutable commit:

1. Every finding-register row is closed with linked test or artifact evidence.
2. Every authoritative repository hard gate in `AGENTS.md` is met for native
   and WASM.
3. Both Rust lockfiles and the npm graph have no known applicable advisories.
4. Bun, Node, Deno, macOS, Linux, Windows, Chromium interop, and real IWA gates
   pass against the packed artifact.
5. Required scale, fault, coverage, 24-hour, and 72-hour evidence is retained.
6. Documentation matches the exact commit and does not overstate evidence.
7. Architect and critic approved the plan before execution.
8. The final independent auto-review reports zero valid P0-P4 findings, and a
   second no-change verification confirms the result.

Until all eight conditions hold, the status remains **not 1.0 ready**.
