## 5. The blocker: the ticker-10k cell cannot be served by this rig or this cable

All three inputs were measured, not estimated.

1. **Frame size.** The relay fans one `relay-to-subscriber` data frame per subscriber per accepted ingress, built at fanout-relay.ts:1235–1250 and encoded per subscriber in `enqueue` (:1280 `this.codec.encode(frame)`); the subscriber parser (fanout-wire.ts:746–770) requires the full envelope (two 64-hex digests, payloadBase64, payloadSha256, ids). Encoding that frame with the repo's own codec for a 100-byte payload: `encodeFanoutWsMessage` → **653 bytes**, `encodeFanoutWtFrame` → **657 bytes** (command: `bun -e` importing `tools/compare/scenarios/fanout-wire.ts`, ids `publisher-000001` / `subscriber-0000NN` per `ROLE_ID_RE` at :332).
2. **Demanded rate.** `ticker-fanout/rate-10000` = 100,000 offered ingress in a 10,000 ms window (cohort-protocol.ts:5617–5624; grant `measuredDurationMs` 10000 from secure_fs.rs:19582; publisher rate = 100000/10 = 10,000/s, compare-controller.ts:4631) × 100 subscribers = **1,000,000 deliveries/s**, 10,000,000 in the window (`expectedExpandedDeliveries`).
3. **Link.** Mac `ifconfig en13` → `media: autoselect (1000baseT <full-duplex,flow-control>)`, inet 10.99.0.1; rig `cat /sys/class/net/eno1/speed` → `1000`, `ip -br addr` eno1 10.99.0.2/24. **1,000 Mbit/s each end.** Declared delivery load = 1,000,000 × 653 B × 8 = **5.22 Gbit/s** before WS/TLS/TCP framing; the cable carries at most ≈190k such deliveries/s, i.e. ≈1.9M in the window and ≈3.8M even if the whole 10 s drain were spent delivering at line rate.
4. **Relay CPU.** The relay is one Bun event loop in the server child (server.ts:687–712: `relay.handleInboundBytes` + `relay.pump()` synchronously in `onMessage`). Same benchmark executed on the rig with the rig's own bun (`/home/hermes-admin/.bun/bin/bun -e` importing `/tmp/ws-wt-linux-build.03pyUO/tools/compare/scenarios/fanout-wire.ts`, idle box, load 0.08, `lscpu`: AMD Ryzen 5 3550H, 2.1 GHz max): **WS 13.49 µs/frame = 74,142 frames/s; WT 14.91 µs/frame = 67,086 frames/s**, single-threaded, encode only — no socket write (the server.ts:850–855 comment measured 1.1 µs per stream write on loopback), no ingress decode, no pump bookkeeping. On this Mac at load 13 the same encode is 5.1/5.7 µs. Against 1,000,000/s demanded that is a 13–15× shortfall on the relay alone.
5. **What the run would actually do.** Ingress arrives at 10,000/s; each accepted ingress costs the relay ≈1.4 ms of encode (100 × 14 µs), so the loop falls behind within the first millisecond of the window; per-subscriber queues are 64 items (fanout-relay.ts:108), so the first `SUBSCRIBER_QUEUE_FULL` close happens after at most 64 accepted ingress per subscriber (:1296–1306), after which `firstBlockedSubscriberCode` makes every further ingress a `closed` ack (:1195–1201, :1858–1866); the publisher books closed acks as acknowledged (fanout-role.ts:836–846) so the drain closes, the workers' subscriber sessions are closed by the relay without an `end` (workers do not fail on that; :1433–1441, :1600–1602), the partials reconcile, and both arms seal PASS with `promotable:false`, accepted ingress in the hundreds to low thousands, deliveries in the tens of thousands, `subscriberEndCount` 0, and a relay fault list the verifier never reads (`faults` at fanout-relay.ts:2416; `grep -n faults verify-artifact.ts` → none). Verifier: `2 PASS`. Wrapper: exit 0, both keys destroyed. B5 stop gate: missed by two orders of magnitude on ingress and deliveries — and only visible if someone runs `reconstructCohortEvidenceOffline` over the seals afterwards.
6. **Consequence for B6.** The same table sends ticker 50k (5M deliveries/s) and ticker 100k (10M/s) into a 12.5-hour canonical campaign that requires all 60 seals `promotable:true`. Those are 26–52 Gbit/s on a 1 Gbit/s cable and 70–150× the rig relay's encode rate. B6 as frozen cannot pass on this hardware either.

This is a plan-level defect (the §4.5 cell table and plan §4.2's 100-byte payload were fixed without the 550-byte wire envelope or the relay's per-subscriber encode in the arithmetic; `grep -nE "Gbit|Mbit|bandwidth"` over the plan and amendment finds no link budget), not a staging defect. It is the class of failure the brief asked for: loopback chat-1k (30k deliveries/s) never exercised it, and A5 moved no fanout traffic.

## 6. What has to change before a B5 launch

One of the following, recorded as an amendment with its own approval, then a new candidate, fresh stage-only and fresh reviews (any of these changes source, so the current staged bytes are abandoned regardless):

- (a) A compact delivery encoding for `relay-to-subscriber` data frames (binary framing keyed by grant/barrier index instead of two 64-hex digests plus base64 plus hex sha per frame) **and** a ticker row whose expansion fits the measured relay and link with margin — e.g. rate-10000 × 100 subscribers is 1M/s and does not fit at any encoding on a 1 Gbit link at 100 B payload (0.8 Gbit/s of payload alone); the row has to shrink (fewer subscribers, lower rate, or both) or the rig has to gain a 10G path and a multi-threaded relay.
- (b) Keep the table and change B5's stop gate to what the verifier can actually prove (topology + conservation) with the observed totals recorded as the pilot's finding — an explicit decision to run a saturation diagnostic, not a completion pilot — and drop or re-scope the ticker rows for B6.
- Either way: implement the §9.6 render clause (topology and totals in the diagnostic report) or record its deviation, so a stop-gate miss is printed rather than inferred; and record the janitor-absent and empty-addon-digest deviations (architect findings 2–3, both re-confirmed here).

Everything else in this stage is clean and does not need to be re-argued after the amendment; the next review can be scoped to the cell/encoding change and the re-frozen command.
